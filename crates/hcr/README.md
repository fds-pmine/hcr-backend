# hcr

Backend service for the HCR Simulator: challenge catalog, authoritative replay
of submitted programs, adaptive sessions, and versus rounds.

The crate carries no transport. `HcrService` takes typed requests and returns
typed responses, opens no sockets, and knows nothing about HTTP, MQTT or
WebSocket framing. An optional adapter behind the `hotaru` feature binds it to
HTTP and ships a deployable server binary.

## Replay is authoritative

A client reports the score it believes it earned. The service does not take that
number. `create_submission` replays the submitted program through
[`hcr_sim`](https://crates.io/crates/hcr_sim) and stores the score it computed
itself. The client's figure is recorded as a claim and compared against the
server's (`diverged`).

That only means something because replay is deterministic, and determinism here
is measured rather than assumed. `hcr_sim` runs against conformance vectors
generated by the TypeScript engine the browser executes, so the two
implementations must agree on kinematics, head safety, voxel sweep and scoring.

## Usage

```toml
[dependencies]
hcr = "0.3"
```

```rust
use hcr::{HcrService, seed::seed_catalog};

let service = HcrService::new(seed_catalog());
```

The HTTP adapter and the server binary come with the `hotaru` feature:

```toml
[dependencies]
hcr = { version = "0.3", features = ["hotaru"] }
```

```sh
HCR_SIGNING_KEY="$(openssl rand -hex 32)" \
HCR_BIND=127.0.0.1:18623 \
HCR_CORS_ORIGIN=https://web.hcr.rs \
cargo run -p hcr --features hotaru --bin hcr-server
```

| Variable | Default | Meaning |
| --- | --- | --- |
| `HCR_SIGNING_KEY` | *required* | HMAC key for item-reference tokens. At least 32 bytes, and stable across restarts: rotating it invalidates every reference in flight. |
| `HCR_BIND` | `127.0.0.1:18623` | Listen address. |
| `HCR_CORS_ORIGIN` | none | Comma-separated allowed browser origins. Absent means no CORS headers at all. |
| `HCR_USAGE_LOG` | none | Path to append usage events to. Omit the variable to record nothing. |

## HTTP surface

Under `/api/v1`: `challenges`, `score`, `cutter-grid/plans`, `submissions`,
`sessions` (with `next`, `responses`, `finalize`), `matches` (with `join`,
`start`, `challenge`, `submissions`, `results`), and `time`. The route table is
`hotaru_binding::ROUTES`. Request and response types live in
[`hcr_contract`](https://crates.io/crates/hcr_contract).

## Bundled certification assets

`assets/` holds two generated files the service embeds at build time.
`cutter-grid-profile-v4.json` is the certified Cutter Grid V4 profile. HTTP
callers can never supply, alter or select a profile body, so the server plans
against this one and no other. `vectors.json` holds the conformance vectors,
which also define the challenge the catalog seeds.

Both files are copies of originals owned elsewhere in the project, vendored
because a published crate can read only what lives under its own directory.
`tests/assets.rs` compares each copy against its original whenever the checkout
that owns the original is present, so the duplicate cannot drift unnoticed. With
only the published crate available, the comparison skips.

## Scope and limits

**No TLS, no authentication layer.** The server speaks plain HTTP and expects a
reverse proxy in front of it. Player identity arrives in the `x-hcr-player`
header, set by whatever validates the bearer token; the service never reads
identity from a request body.

**Cutter Grid planning is server-owned.** Clients submit a program. They cannot
submit a profile or a trajectory.

**Adaptive selection comes from [arona](https://crates.io/crates/arona)**, with
the HCR item bank layered on top by
[`hcr_qbank`](https://crates.io/crates/hcr_qbank).

This crate is std-only. The `no_std` targets in the same project are
[`hcr_contract`](https://crates.io/crates/hcr_contract) and
[`hcr_sim`](https://crates.io/crates/hcr_sim).
